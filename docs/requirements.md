## F-01. 다중 소스 뉴스 수집 파이프라인

**개요**
네이버 뉴스 검색 API와 The Guardian Open Platform API로부터 주기적으로 뉴스를 수집하여, 중복을 제거한 뒤 데이터베이스에 정규화된 형태로 저장한다.

**입력**
| 항목 | 설명 |
|---|---|
| 수집 대상 API | 네이버 뉴스 검색 API(**NAVER API HUB** — 개발자센터 검색 API는 2026-07-31 신규 발급 종료로 이관, 현재 무료 체험·검색 전체 월 775,000회), The Guardian Open Platform API |
| 검색 키워드/카테고리 | 사전 정의된 카테고리 8개(기본안 — 디자인 목업의 카테고리 칩과 최종 대조 필요): 정치, 경제, 사회, 국제, IT·과학, 생활·문화, 스포츠, 연예. 코드 위치: `backend/src/news/types.ts` |
| 폴링 주기 | 네이버 10분 / Guardian 30분 (node-cron 스케줄 기준). Guardian 무료 키 한도(하루 500회, 초당 1회)를 넘지 않도록 설정 |

**처리 로직**
1. node-cron이 설정된 주기마다 트리거된다.
2. 네이버는 카테고리마다 구체적인 검색 키워드 2~3개로 요청(sort=date, 키워드별 1회)하고, Guardian은 카테고리 구분 없이 최신 기사를 한 번에 요청한 뒤 응답의 section 필드로 카테고리를 매핑한다.
3. 응답받은 각 기사 데이터를 공통 포맷으로 정규화한다: `{ title, description, source, category, original_link, published_at }`
   - 네이버 응답에는 언론사명·카테고리가 없음(title, originallink, link, description, pubDate만 제공)
   - source: originallink의 도메인을 언론사명 매핑 테이블(예: chosun.com → 조선일보)로 변환, 매핑에 없으면 도메인 그대로 저장
   - category: 검색에 사용한 카테고리로 지정. 같은 기사가 여러 카테고리 검색에 걸리면 먼저 검색한 카테고리를 유지(기사당 카테고리 1개). 검색 순서는 주제가 뚜렷한 카테고리부터(연예→스포츠→경제→정치→국제→IT·과학→사회→문화)
   - (2026-10-02) '국제'·'IT 과학'처럼 넓은 단어 하나로 검색하면 오분류가 많아 구체적 키워드 여러 개로 변경. 키워드 방식의 한계(특히 IT·과학)는 F-04 착수 시 AI 분류 도입 여부로 재검토
   - 네이버 title/description의 HTML 태그(`<b>`)와 엔티티(`&quot;` 등) 제거
   - originallink가 비어 있으면 link 사용
   - published_at은 timestamptz로 통일(네이버 RFC1123 KST, Guardian ISO 8601 UTC)
4. original_link 또는 title+source 조합 기준으로 기존 DB에 이미 존재하는 기사인지 확인한다.
5. 신규 기사만 articles 테이블에 저장한다.
6. 신규 기사가 저장되면 F-02(실시간 피드)를 트리거하는 이벤트를 발생시킨다.
7. 보관 정책(기본안): 어떤 보드에도 올라가지 않은 수집 기사는 30일이 지나면 삭제한다(하루 1회 정리 작업).

**출력**
- DB에 저장된 신규 기사 레코드
- 신규 기사 저장 이벤트(F-02 트리거용)

**예외 처리**
| 상황 | 처리 방안 |
|---|---|
| API 요청 실패(타임아웃, 5xx 오류) | 로그 기록 후 다음 폴링 주기에 재시도. 즉시 재시도는 하지 않음(연쇄 실패 방지) |
| API 일일 쿼터 초과 | 해당 API 호출을 그날 남은 시간 동안 중단하고 경고 로그 기록. 다른 API는 정상 수집 지속 |
| 응답 데이터 형식 오류(필드 누락 등) | 해당 기사 건너뛰고 나머지 계속 처리, 오류 건수 로깅 |
| 중복 판별 실패(동일 기사가 다른 링크로 중복 수집) | 1차는 original_link 기준, 추후 제목 유사도 기반 2차 필터링으로 고도화 가능(초기 스코프에서는 생략 가능) |

**수용 기준 (완료 판단 기준)**
- [ ] 설정된 주기마다 자동으로 폴링이 실행된다
- [ ] 네이버·Guardian 두 소스 모두에서 정상적으로 기사를 수집한다
- [ ] 동일 기사가 중복 저장되지 않는다
- [ ] API 실패 시 전체 파이프라인이 중단되지 않고 다음 주기에 정상 복구된다
- [ ] 쿼터 초과 시에도 서비스 전체가 다운되지 않는다

**관련 기술**: Node.js, node-cron, 네이버 뉴스 검색 API, The Guardian Open Platform API, PostgreSQL

## F-02. WebSocket 기반 실시간 뉴스 피드

**개요**
F-01에서 신규 기사가 저장되면 Socket.io를 통해 접속 중인 클라이언트에게 즉시 브로드캐스트하여, 새로고침 없이 화면에 반영한다.

**입력**: F-01의 "신규 기사 저장" 이벤트, 클라이언트의 room 구독 정보(news-feed room)

**처리 로직**
1. 클라이언트가 접속하면 Socket.io news-feed room에 join한다.
2. F-01에서 신규 기사가 저장되면 서버가 수집 1회분을 최신순으로 묶어 io.to('news-feed').emit('feed:new-articles', { articles, total, truncated })를 호출한다. 한 번에 최대 50건만 보내고, 넘치면 truncated=true로 알린다 (2026-10-02 변경: 기사 1건당 이벤트 1번은 첫 수집 때 수천 번 emit되어 묶음 방식으로 바꿈).
3. 클라이언트는 이벤트 수신 시 피드 최상단에 새 카드를 추가한다. truncated면 REST로 최신 목록을 다시 조회한다.
   - REST: `GET /api/articles?limit=30&category=&before=<커서>` — 최신순, 커서 기반 "더 보기". user_submitted 기사는 제외
4. (고도화) 키워드/카테고리별로 room을 세분화(news-feed:{category})해 관심사 기반 구독 지원.

**출력**: 클라이언트 화면에 실시간 반영된 새 기사 카드

**예외 처리**
| 상황 | 처리 방안 |
|---|---|
| 소켓 연결 끊김 | 재연결 시 REST API로 최근 기사 목록을 재조회해 누락분 보완 |
| 다수 동시 접속 시 브로드캐스트 부하 | 초기 스코프는 단일 서버로 충분. 확장 필요 시 Redis Adapter 검토(현재는 제외) |
| 이벤트 발송 실패 | 로그 기록. 클라이언트는 재연결 시 REST 재조회로 상태 복구 |

**수용 기준**
- [ ] 새 기사가 저장되면 3초 이내 접속자 화면에 반영된다
- [ ] 재연결 시 끊긴 동안 놓친 기사도 확인 가능하다
- [ ] 다수 클라이언트 동시 접속에서도 정상 브로드캐스트된다

**관련 기술**: Socket.io, Node.js, WebSocket

## F-03. 사용자 링크 기반 AI 요약 카드 생성

**개요**
사용자가 뉴스 URL을 붙여넣으면 서버가 본문을 추출하고 AI가 요약하여, API로 수집된 기사와 동일한 카드 형태로 저장한다.

**입력**: 사용자가 입력한 URL

**처리 로직**
1. URL 유효성 검사 (SSRF 방지)
   - http/https만 허용
   - 호스트를 DNS로 조회한 **실제 IP** 기준으로 사설 IP·loopback·link-local(169.254.x.x 등) 차단 (URL 문자열만 검사하면 우회 가능)
   - 리다이렉트는 최대 3회, 매 단계마다 같은 검사 반복
   - 타임아웃 5초, 응답 크기 2MB 제한
   - 중복 판별 전 URL 정규화(utm_* 등 추적 파라미터 제거, m. 모바일 도메인 통일)
2. 서버가 해당 페이지를 fetch하고 본문 추출 라이브러리로 본문 텍스트를 추출 (실패 시 og:description 메타태그로 폴백)
3. 추출된 본문을 AI 요약 API(OpenAI)에 전달해 2~3줄 요약 생성
4. title, description(AI 요약), source(도메인), original_link, published_at으로 정규화해 articles 테이블에 저장, source_type='user_submitted'로 구분 (published_at은 확인 불가 시 null, 제출자는 submitted_by에 기록)
5. 생성된 카드를 보드에 추가 가능하도록 반환
6. 노출 범위(기본안): user_submitted 기사는 전체 뉴스 피드(F-02)에 브로드캐스트하거나 검색(F-04)에 노출하지 않고, 추가된 보드 안에서만 보인다.

> ℹ️ 국내 언론사는 봇 차단·페이월·JS 렌더링 페이지가 많아 본문 추출이 자주 실패할 수 있음. og 태그 폴백이 주 경로가 될 수 있다는 전제로 구현.
>
> ⚠️ 프롬프트 인젝션 대비(추후 진행): 사용자가 넣은 페이지 본문은 지시가 아닌 데이터로 취급하도록 프롬프트를 구성하고, 출력 길이·형식을 제한한다.

**출력**: 신규 기사 카드(AI 요약 포함)

**예외 처리**
| 상황 | 처리 방안 |
|---|---|
| URL이 사설 IP/localhost를 가리킴 | 요청 차단, 사용자에게 에러 안내 (SSRF 방지) |
| 본문 추출 실패 | og:description만으로 카드 생성, 완전 실패 시 "요약할 수 없는 페이지" 안내 |
| AI API 실패/타임아웃 | 1회 재시도 후 실패 시 에러 반환 |
| 동일 URL 중복 제출 | 이미 존재하는 카드로 안내 |

**수용 기준**
- [ ] 일반적인 뉴스 URL 입력 시 정상적으로 요약 카드가 생성된다
- [ ] 사설 IP/localhost 등 위험한 URL은 차단된다
- [ ] 본문 추출 실패 시에도 서비스가 중단되지 않고 대체 정보로 카드가 생성된다

**관련 기술**: Node.js, 본문 추출 라이브러리(article-extractor 등), OpenAI API

## F-04. 뉴스 검색/필터

**개요**
수집된 기사 중 키워드, 카테고리, 언론사 기준으로 검색·필터링하는 기능.

**입력**: 검색 키워드, 카테고리, 언론사, 기간

**처리 로직**
1. 기본은 title/description에 대한 LIKE 기반 키워드 검색
2. 카테고리/언론사/기간은 WHERE 조건으로 필터링
3. (고도화) pgvector 기반 시맨틱 검색으로 의미상 유사한 기사까지 검색 지원

**출력**: 조건에 맞는 기사 목록

**예외 처리**: 검색 결과 없음 → 빈 목록 반환 및 안내 문구 표시. 검색어 없이 필터만 단독 적용도 가능.

**수용 기준**
- [ ] 키워드로 기사 제목/요약 검색이 가능하다
- [ ] 카테고리/언론사/기간 필터가 정상 동작한다

**관련 기술**: PostgreSQL (LIKE/WHERE), (고도화) pgvector

## F-05. 실시간 협업 보드

**개요**
여러 사용자가 동시에 접속해 기사·메모·사진 카드를 보드 위에 자유롭게 배치하고 실시간으로 동기화하는 기능.

**입력**: 사용자의 카드 추가/이동/삭제/수정 액션

**처리 로직**
1. 사용자가 보드 접속 시 board:{boardId} room에 join한다.
2. 카드 추가/이동/삭제 시 클라이언트가 즉시 로컬에 반영(Optimistic Update)한 뒤 서버에 이벤트를 전송한다 (card:add, card:move, card:delete, memo:add 등).
3. 서버는 DB(board_items)에 반영 후 같은 room의 다른 참여자에게 브로드캐스트한다.
4. 변경 로그를 board_events에 기록한다 (히스토리 조회용. 되돌리기(undo)는 이번 범위에서 제외 — 기본안).
5. 드래그 중에는 card:moving 이벤트를 50–100ms 간격으로 스로틀링해 브로드캐스트만 하고 DB에는 저장하지 않는다. 드래그가 끝났을 때(card:move) 한 번만 board_items·board_events에 저장한다.
6. 서버는 모든 변경 이벤트에 ack로 성공/실패를 응답하고, 실패 시 클라이언트는 Optimistic Update를 롤백한다.
7. 사진 카드는 S3 비공개 버킷에 저장한다. 업로드·조회 모두 presigned URL을 사용하고, jpg/png/webp만 허용, 최대 10MB. 카드 삭제 시 S3 객체도 삭제한다.

**출력**: 모든 참여자에게 동기화된 보드 카드 상태

**예외 처리**
| 상황 | 처리 방안 |
|---|---|
| 동시에 같은 카드를 수정 | 초기 버전은 last-write-wins로 단순화. 이후 필요 시 락/버전 관리로 고도화 |
| 연결 끊김 | 재연결 시 현재 보드 스냅샷을 다시 불러와 동기화 |
| 이미 삭제된 카드에 대한 액션 시도 | 무시하고 에러 로그 기록 |

**수용 기준**
- [ ] 두 명 이상 동시 접속 시 한 명의 변경이 즉시 다른 사람 화면에 반영된다
- [ ] 재연결 시 보드 상태가 정확히 복원된다
- [ ] 기사·메모·사진 세 가지 카드 타입 모두 추가·이동·삭제가 가능하다

**관련 기술**: Socket.io, react-konva, PostgreSQL(board_items, board_events)

## F-07. 최소 인증 + 보드 세션(초대) 관리

**개요**
로그인 기능과, 초대 링크를 통해 보드에 참여자를 추가하는 기능.

**입력**: 이메일/비밀번호 또는 카카오·네이버 소셜 로그인, 초대 링크 토큰

**처리 로직**
1. 회원가입/로그인 시 JWT 발급 (카카오·네이버 소셜 로그인은 각 OAuth 연동 후 동일하게 JWT 발급)
2. 보드 생성 시 고유 토큰의 초대 링크 발급
3. 초대 링크로 접속한 사용자를 board_members에 자동 추가 (로그인 필요)
4. WebSocket 연결 시에도 JWT를 검증해 인증된 사용자만 보드 room에 join 가능 (room join 시 board_members 소속 여부도 확인)
5. 토큰 정책(기본안): access token(15분)과 refresh token(14일)을 httpOnly·Secure 쿠키로 발급. refresh token은 해시해 refresh_tokens 테이블에 저장하고 로그아웃 시 폐기
6. 초대 링크 정책(기본안): 유효기간 7일, 만료 전까지 여러 명이 사용 가능, owner가 재발급하면 기존 링크 무효화. 비로그인 사용자는 로그인(OAuth state에 복귀 경로 포함) 후 초대 페이지로 자동 복귀
7. 권한(기본안): owner — 보드 삭제·이름 변경·초대 링크 재발급·멤버 내보내기 / editor — 카드 추가·수정·삭제

8. 구현 범위 (2026-10-02): 1단계로 이메일 가입·로그인, 토큰 회전(refresh token 1회용), 로그아웃, 보호 API·소켓 연결 인증 구현. **뉴스 피드도 로그인 사용자만** 볼 수 있다(설계 원칙 5). 카카오·네이버 소셜 로그인은 키 발급 후 2단계, 초대 링크(2~3)는 boards 테이블이 생기는 F-05에서 구현
9. 보안: 상태를 바꾸는 요청은 Origin이 APP_ORIGIN일 때만 허용(CSRF 방지), 소켓도 Origin 확인. 같은 IP+이메일로 15분 안에 5번 틀리면 로그인 일시 차단(429). 없는 이메일과 틀린 비밀번호는 같은 메시지·같은 처리 시간으로 응답(가입 여부 노출 방지). 비밀번호는 scrypt 해시로만 저장

**출력**: 인증 토큰, 보드 참여자 목록

**예외 처리**: 만료·잘못된 초대 토큰 → 에러 안내 / 인증되지 않은 WebSocket 연결 시도 → 연결 거부

**수용 기준**
- [ ] 로그인하지 않으면 보드에 접속할 수 없다
- [ ] 초대 링크로 새 참여자가 정상적으로 추가된다
- [ ] WebSocket 연결도 인증 없이는 거부된다

**관련 기술**: JWT, Node.js

## F-08. AI 이슈 클러스터링 및 요약

**개요**
보드에 모인 기사들을 임베딩 기반 유사도로 자동 그룹핑하고, 각 그룹을 AI가 한 줄로 요약해주는 기능.

**입력**: 보드 내 기사 카드들의 title+description

**처리 로직**
1. 기사가 보드에 처음 추가될 때 title+description을 OpenAI Embedding API(text-embedding-3-small)로 벡터화해 articles.embedding에 저장 (수집한 모든 기사를 임베딩하지 않음. 이미 임베딩된 기사는 재사용)
2. 클러스터링 요청 시 보드 내 기사 임베딩을 불러와 서버 메모리(Node)에서 코사인 유사도를 계산 (보드당 기사가 수십 개 수준이라 DB 벡터 연산·인덱스 불필요)
3. 평균 연결(average linkage) 계층적 군집화로 그룹핑하고 유사도 임계값(설정값)에서 자른다. 기사 1개짜리 그룹은 클러스터로 만들지 않는다. (단순 임계값 비교만으로는 A–B, B–C가 유사해도 A–C가 다를 수 있어 결과가 정해지지 않음)
   - 한국어·영어 기사는 한 클러스터로 묶을 수 있음(기본안). 다만 같은 언어끼리보다 유사도가 낮게 나오므로 임계값은 실제 데이터로 조정
4. 클러스터별로 AI에게 요약을 요청("이 그룹의 핵심 이슈는?")
5. 클러스터 결과와 요약을 보드에 표시, 사용자가 수동으로 재배치 가능
6. "자동 정렬" 시 각 카드의 현재 좌표를 prev_position_x/y에 저장하고, "원래대로" 시 그 좌표로 복원
7. 다시 클러스터링하면 해당 보드의 기존 클러스터(clusters/cluster_items)를 새 결과로 교체. 카드 좌표는 사용자가 "자동 정렬"을 누르기 전까지 바뀌지 않음

**출력**: 클러스터 그룹 및 요약 텍스트

**예외 처리**: 임베딩 API 실패 시 해당 기사는 클러스터링에서 제외하고 개별 카드로만 표시 / 클러스터링 결과가 부적절할 경우(전부 한 그룹 또는 전부 별개) 유사도 임계값을 설정값으로 분리해 조정 가능하게 함

**수용 기준**
- [ ] 관련 있는 기사들이 실제로 같은 그룹으로 묶인다
- [ ] 각 그룹에 대해 AI 요약이 표시된다
- [ ] 사용자가 클러스터링 결과를 무시하고 수동으로 재배치할 수 있다

**관련 기술**: OpenAI Embedding API, pgvector, PostgreSQL, OpenAI API
