# 모여봄 — 기획/설계서

> Notion "기획/설계서" 페이지와 동기화됨 (최종 반영: 2026-09-30)

> 1인 기획 + AI 코딩 에이전트(Claude Code)에게 개발·디버깅을 위임하는 방식으로 진행. 아래 내용은 캡스톤 발표(PPT)까지 완료된 시점 기준으로 확정된 기획안입니다.


## 1. 프로젝트 개요 (Overview)
- **프로젝트명:** 모여봄
- **부제:** 흩어진 뉴스를, 팀이 실시간으로 함께 모으고 정리하며 맥락을 파악하는 공동 리서치 브리핑 툴
- **핵심 가치:**
- **Information Curation:** 여러 언론사의 뉴스를 AI가 수집·요약하여 한눈에 파악.
- **Real-time Collaboration:** 여러 사용자가 동시에 하나의 보드 위에서 기사를 스크랩하고 정리.
- **Visual Organization:** 탐정보드/핀터레스트 스타일로 기사, 메모, 이미지를 자유롭게 배치.
- **차별점 (경쟁 서비스 대비):** 뉴스 큐레이션 앱(뉴닉·캐리 등)은 자동 수집만 있고 협업이 없음. 범용 화이트보드(Miro 등)는 협업은 강력하나 뉴스 자동 수집이 없음. 모여봄은 "자동 수집 + 실시간 협업 + AI 정리" 3요소가 하나의 흐름으로 이어진 것이 핵심 차별점.

## 2. 주요 기능 (Key Features)

상세 명세는 `docs/requirements.md` (F-01~F-13) 참조.

### 2.1. 뉴스 수집 & AI 요약 [뉴스 트랙]
- 네이버 뉴스 검색 API, The Guardian Open Platform API로 기사를 수집해 WebSocket 기반 실시간 피드로 제공.
- 주제/키워드/언론사 기준 검색 및 필터링.
- 사용자가 기사 링크를 붙여넣으면 AI가 본문을 요약해 API 수집 기사와 동일한 카드 포맷으로 변환.
- **(Could)** 사용자가 고른 주제/키워드를 지정 시간에 AI가 요약해 발송하는 예약 다이제스트 (예: 매일 오전 8시 경제 뉴스 요약).

### 2.2. 실시간 협업 화이트보드 [협업 트랙]
- 여러 사용자가 동시 접속해 하나의 보드에서 기사를 스크랩하고 스티키 메모·이미지를 추가, 탐정보드 스타일로 자유 배치.
- AI가 스크랩된 기사를 임베딩 기반 유사도로 주제별 자동 클러스터링·요약.
- **(Could)** AI 클러스터링 이후 사용자가 카드 간 연결선을 수동으로 추가/조정하는 스레드형 시각화. 핵심 기능 완료 후 비주얼 폴리시 단계에서 진행.
- **(Should)** 보드 내 언론사 편중 여부를 보여주는 출처 다양성 표시.
- **(Could)** 보드에 모인 기사 내용을 근거로 자연어 질문에 답하는 보드 기반 질의응답(RAG).
- **(Low priority)** 반대 관점 기사 추천, 시간이 허락할 때만 시도.

### 2.3. 보드 관리 및 인증
- 최소 인증(로그인: 이메일/비밀번호 또는 카카오·네이버 소셜 로그인) + 초대 링크 기반 보드 세션 관리.
- 보드 목록/대시보드에서 참여 중인 보드 조회 및 새 보드 생성.
- **범위 제외:** Fact vs Opinion 기사 태깅 기능은 AI 판단의 한계 및 오해 소지로 완전히 제외.

## 3. 기술 스택 (Technical Stack)

| 구분 | 기술 스택 | 비고 |
|---|---|---|
| 언어 | JavaScript / TypeScript | 프론트-백엔드 동일 언어로 WebSocket 로직 재사용 |
| 프론트엔드 | React + TypeScript | react-konva로 캔버스 기반 화이트보드 구현 |
| 백엔드 | Node.js (Express) | WebSocket을 적극 활용하는 실시간 협업 로직 |
| 실시간 통신 | Socket.io | 보드별 room 단위 동시 편집 동기화 |
| 데이터베이스 | PostgreSQL + pgvector | 관계형 데이터와 AI 임베딩 검색을 하나의 DB에서 함께 처리 (별도 벡터 DB 불필요) |
| 뉴스 API | 네이버 뉴스 검색 API(NAVER API HUB), The Guardian Open Platform API | 본문 전체 대신 요약(description)+원문 링크 방식으로 저작권 리스크 최소화 |
| AI API | OpenAI API (Embedding + 요약) | 이슈 클러스터링용 임베딩 생성, 기사·링크·클러스터 요약. 2026-09-30: 기존에 사용하던 OpenAI API로 통일해 키·결제 관리를 한 곳으로. 기능별 모델은 개발 시 확정 |
| 스토리지 | AWS S3 | 사진 카드(핀터레스트 스타일) 이미지 업로드. 비공개 버킷 + presigned URL |
| 인증 | JWT + 카카오·네이버 OAuth | 2026-09-21: GitHub/Google 소셜 로그인에서 국내 타겟에 맞게 카카오·네이버로 변경. 토큰은 httpOnly 쿠키 |

## 4. 백엔드 상세 설계 명세 (Backend Specification)

### 4.1. 실시간 동기화 전략 (Socket.io Room)
- **Key:** `board:{boardId}` room 단위로 접속자 그룹화.
- **이벤트:** `card:add`(기사·메모 공통), `card:move`, `card:update`(메모 내용), `card:delete` 등 보드 내 변경사항을 room 전체에 브로드캐스트 (클러스터 이벤트는 F-08에서 추가). 드래그 중에는 `card:moving`을 50–100ms 간격으로 스로틀링해 브로드캐스트만 하고, 드래그가 끝난 `card:move` 시점에 한 번만 DB에 저장. 전체 목록은 요구사항 명세서 F-05 처리 로직 8번.
- **Optimistic Update:** 클라이언트에서 즉시 반영 후 서버 브로드캐스트로 동기화. 서버는 모든 변경 이벤트에 ack로 성공/실패를 응답하고, 실패 시 클라이언트가 롤백.
- 충돌 처리는 초기 버전에서 last-write-wins로 단순화, 이후 필요 시 락/버전 관리로 고도화.

### 4.2. 뉴스 수집 파이프라인
- node-cron 스케줄러가 네이버는 10분, Guardian은 30분 주기로 API를 호출(Guardian 무료 키 하루 500회 한도 고려) → 원문 URL 기준 중복 제거 → DB 저장 → 신규 기사 저장 시 WebSocket 이벤트 발생.
- 사용자 링크 추가 시: 본문 텍스트 추출 → AI 요약 모델 호출 → API 수집 기사와 동일 스키마로 저장.
- API 실패·쿼터 초과 시에도 전체 파이프라인이 중단되지 않도록 예외 처리 (다음 주기 재시도, 로그 기록).

### 4.3. AI 클러스터링 전략
- 기사가 보드에 처음 추가될 때 제목+요약을 OpenAI Embedding API(text-embedding-3-small, 1536차원)로 벡터화하여 pgvector 컬럼에 저장.
- 보드 내 기사(수십 개 수준)의 임베딩을 불러와 서버 메모리에서 코사인 유사도를 계산하고, 평균 연결 계층적 군집화 + 유사도 임계값으로 클러스터 그룹핑.
- 클러스터 결과를 보드에 자동 배치하고, 사용자가 수동으로 재배치 가능하도록 함.

## 5. 데이터 흐름 (Data Flow)

1. **뉴스 소스(네이버·Guardian API)** → **수집 파이프라인** (폴링·정규화·중복 제거) → **DB(PostgreSQL) 저장**
2. **DB 저장 이벤트** → **Socket.io** → **실시간 피드** (접속자 화면에 즉시 반영)
3. **사용자** → 기사를 **협업 보드**로 드래그 배치, 또는 링크 직접 입력(→ AI 요약 → 카드 생성)
4. **협업 보드의 변경사항** → **Socket.io Room** → 보드 참여자 전체에 실시간 브로드캐스트
5. **보드 내 기사** → **임베딩 생성(OpenAI, pgvector 저장) + 보드 단위 유사도 계산** → **AI 클러스터링 결과** → 보드에 자동 반영

---

## 6. 핵심 설계 원칙

1. **실시간성 우선:** 보드 위 모든 변경은 WebSocket으로 즉시 전파되어야 함.
2. **AI는 보조 도구:** 요약·클러스터링 결과는 추천일 뿐, 사용자가 언제든 수동으로 조정 가능해야 함.
3. **핵심 기능 우선:** 예약 다이제스트, RAG 등 부가 기능은 MVP 이후 단계에서 도입하고, 카드 연결선은 핵심 기능 완료 후 비주얼 폴리싱 단계에서 진행.
4. **확장성:** 뉴스 트랙과 협업 트랙을 느슨하게 결합하여 독립적으로 확장 가능하도록 설계.
5. **저작권 고려:** 기사 본문은 저장하지 않고 요약+원문 링크 방식으로 설계, 상업적 이용이 명시적으로 허용된 API 위주로 조합.
